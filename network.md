# plan_network.md

## Domain: Infrastructure & Plumbing

**Target Files:** `relay_node.py`, `directory_api.py`, `docker-compose.yml`, `Dockerfile.headless`

### 1. Integration Contract

- **Role:** Wire-level transmission, connection multiplexing, and network state registry.
- **Inputs/Outputs:** Accepts and delivers exactly 4096-byte network packets. It assumes all payloads generated by the Cryptography domain are perfectly formed.
- **Agnosticism:** This domain does not construct encryption envelopes. It handles sockets, asynchronous event loops, and REST API directory registration.

### 2. Docker Infrastructure & Topology

The system operates on a single isolated Docker bridge network named `i2i-mesh`. DNS resolution is handled internally by Docker via service names. The network context is identified via the `I2I_IN_DOCKER=true` environment variable.

#### 2.1 Service Mappings

- **Directory Server:** Uses `Dockerfile.headless`. Maps host port `5001:5001`.
- **Relay Nodes (1-4):** Uses `Dockerfile.headless`. Exposes no ports to the host; internal `i2i-mesh` routing only. (Relay 3 acts as the Gateway Relay, which is a standard relay that also holds Bob's registered listener socket).

#### 2.2 Dockerfile.headless Definition

Minimal execution environment. Uses `python:3.10-slim-bookworm` with Python dependencies only. No GUI or X11 stack is included. Used exclusively to run `relay_node.py` or `directory_api.py`.

### 3. Directory API Contracts

The directory is a stateless Flask server operating at `http://directory:5001`. All state is volatile and cleared upon restart. Nodes and clients must re-register every 30 seconds.

#### 3.1 Registration & LeaseSets

The API enforces a strict distinction between Relay node registration and Client LeaseSet registration. Both payloads must contain a `timestamp` and a full `signature`.

- **Relay Fields:** Requires `ed25519_pubkey`, `x25519_pubkey`, `ip`, and `port`.
- **LeaseSet Fields (Clients):** Requires `ed25519_pubkey`, `x25519_pubkey`, `gateway_ip`, and `gateway_port`.

#### 3.2 Security Validation

The Flask API enforces three validation checks on every POST request:

1.  **Timestamp Jitter:** The `timestamp` is checked against server time to prevent replay registrations.
2.  **Rate Limiting:** Prevents registration spam.
3.  **Signature Verification:** The entire payload must be signed by the `ed25519_pubkey` and validated before acceptance.

### 4. Relay Node Core Operations

Relay nodes (`relay_node.py`) are headless TCP servers responsible for routing and delaying packets. A general network connection timeout of 30 seconds is enforced on all socket operations.

#### 4.1 Asynchronous Concurrency Model

Relay nodes must be 100% asynchronous. The server is instantiated via `asyncio.start_server`. Absolutely no blocking socket calls (`socket.recv`, `socket.connect`) are permitted.

#### 4.2 The 4096-Byte Strict Read

Every inbound network read must enforce the 4096-byte invariant.
The implementation must use `await reader.readexactly(4096)`. Variable-length buffering or reads are strictly prohibited.

#### 4.3 Trial-Peeling Loop

Upon receiving a 4096-byte packet, the relay node executes the trial-peeling workflow:

1.  Attempt to decrypt the outer layer using the relay's cached X25519 Private Key.
2.  Relies on catching PyNaCl `CryptoError` exceptions. If a `CryptoError` is caught, the relay knows it is not the intended recipient of that layer.
3.  If decryption succeeds, the relay strips its layer, reads the 64-byte structural header (Next_IP, Next_Port), and applies padding to restore the exact 4096-byte size.

#### 4.4 Artificial Routing Delay

To resist traffic analysis, every relay node must apply an artificial delay of 0.5 to 2.0 seconds between successfully peeling a layer and forwarding/delivering the packet.

#### 4.5 Nonce TTL Sweep

To prevent network-level replay attacks, relays store observed 24-byte nonces. Memory bloat is prevented via an independent `asyncio` task that runs exactly every 60 seconds to sweep and purge expired nonces.

### 5. Phased Execution Plan (Network Scope)

The Master Specification defines a 7-phase execution plan. This domain manages the middle phases.

- **Goal:** Establish the stateless directory registry and 100% asynchronous, non-blocking wire transmission.
- **Steps:**
  1. Stand up the `i2i-mesh` Docker network and `Dockerfile.headless` containers.
  2. Build the Flask Directory API and strict signature validation logic.
  3. Implement the `asyncio` Relay TCP servers with exact 4096B reads.
  4. Implement trial peeling, the 0.5–2.0s artificial delay, and the 60s nonce sweep.
- **Gate:** Docker services communicate over internal DNS. Relays successfully post distinct Relay parameters to the directory. Relays successfully pass mocked 4096B payloads between each other utilizing the delay.
